# FOMO Terminal — отдельный инстанс terminal.fomo.spot

Тот же код, второй экземпляр: свой checkout (`/opt/fomo-terminal`), свой `.env`, **своя база PostgreSQL и свои пользователи**,
свой процесс pm2 (`fomo-terminal`) на другом порту, свой vhost nginx. С `fomo.spot` не общего ничего: ни базы, ни
`AUTH_SECRET`, ни cookie, ни ключей; **единственное исключение: аккаунт и профиль зеркалируются между двумя базами** (раздел
«Единый аккаунт» ниже). Режим включается переменными окружения; если они не заданы, `fomo.spot` ведёт себя
ровно так же, как раньше.

В копии есть только: Терминал (календарь — вкладка внутри него), уведомления (колокольчик, push, Telegram, e-mail, Android), профиль
(вкладки «Профиль», «Безопасность», «Настройки уведомлений») и админка для владельца инстанса. Доски идей, чата, каналов,
авторов, калькулятора, платежей, подписок, комнат, справки нет.

## Как включается режим

| Переменная | Когда читается | Значение |
|---|---|---|
| `SITE_MODE=terminal` | во время работы (сервер, API, рассылка, метаданные) | включает режим |
| `NEXT_PUBLIC_SITE_MODE=terminal` | **при сборке** (клиентский код, middleware) | то же значение; после смены — пересборка |
| `NEXT_PUBLIC_SITE_URL=https://terminal.fomo.spot` | при сборке и во время работы | публичный адрес: canonical, sitemap, robots, письма, ссылки уведомлений |
| `AUTH_URL`, `NEXTAUTH_URL` = тот же адрес | во время работы | next-auth; по ним же решается, нужны ли `Secure`-cookie |
| `AUTH_SECRET`, `NEXTAUTH_SECRET` | во время работы | **свой** секрет инстанса (`openssl rand -base64 48`) |
| `AUTH_COOKIE_PREFIX` | необязательно | по умолчанию в режиме terminal — `terminal` |
| `EMAIL_FROM` | необязательно | иначе `FOMO Terminal <no-reply@fomo.spot>` |
| `TERMINAL_CONTACT_EMAIL` | во время работы, необязательно | публичный адрес для связи, он печатается на `/privacy` и `/terms` (раздел «Контакты»). Пусто = на страницах написано «через форму обратной связи на https://fomo.spot», адрес не показывается. Личную почту сюда не ставить |
| `GOOGLE_SITE_VERIFICATION` | во время работы, необязательно | содержимое (`content`) метатега Google Search Console; пусто = тега нет |
| `YANDEX_VERIFICATION` | во время работы, необязательно | содержимое метатега Яндекс.Вебмастера; пусто = тега нет |
| `ACCOUNT_MIRROR_SECRET` | во время работы, **на обоих инстансах одинаковый** | общий секрет подписи зеркала аккаунтов (не короче 32 символов). Нет секрета или адреса пира = зеркало **выключено** |
| `ACCOUNT_MIRROR_PEER_URL` | во время работы | origin **другого** инстанса по loopback: у fomo.spot `http://127.0.0.1:3100` (порт терминала), у терминала `http://127.0.0.1:3000` (порт fomo.spot). Не публичный https-адрес |

Без `SITE_MODE` / `NEXT_PUBLIC_SITE_MODE` сайт — обычный fomo.spot (`siteUrl()` = `https://fomo.spot`, cookie
`authjs.*`, все страницы). Логика: `src/lib/site-mode.ts`, проверка: `npx tsx scripts/check-site-mode.ts`.

### Что делает режим terminal

- **Страницы — allowlist** (`routeAllowed`, middleware): `/`, `/login`, `/register`, `/forgot-password`, `/terminal`,
  `/profile`, `/calculator`, `/privacy`, `/terms`, `/admin`, `/admin/users`, `/admin/broadcast`, `/admin/site-settings`.
  `/calculator` — калькулятор риска и размера позиции (фьючерсы Мосбиржи; данные контракта — `GET /api/futures/spec` из публичного ISS, без БД и без идей); в приложении — вкладка дока «Калькулятор» (после «Терминала»; также профиль → «Калькулятор» и карточка в терминале по фьючерсу), входа требует так же, как `/terminal`.
  Всё остальное (в т. ч. любые новые страницы) — редирект на `/terminal` (закрытые разделы админки — на `/admin`).
  `/` для гостя — лендинг «FOMO Terminal» (`TerminalLanding`), для вошедшего — редирект на `/terminal`.
  Отдельной страницы `/calendar` и страницы `/terminal/features` нет: `/calendar` ведёт на `/terminal?panel=calendar` (открывает вкладку
  «Календарь»; так же работают старые ссылки напоминаний `/calendar#дата`), `/terminal/features` — на `/terminal`.
- **Вход обязателен, гостевого демо нет**: `/terminal*`, `/calculator` (и `/calendar`) для гостя — редирект на `/login?callbackUrl=<путь>`
  (middleware, `terminalNeedsLogin` в `site-mode.ts`); после входа человек попадает на запрошенную страницу (по умолчанию `/terminal`).
  Публичны только `/`, `/privacy`, `/terms`, `/login`, `/register`, `/forgot-password`. **Публичные API с рыночными данными**
  (`klines`, `quote(s)`, `market-search`, `orderbook`, `news`, `economic-calendar` и др.) по-прежнему открыты без входа: закрывать их
  было бы отдельной задачей (могут ломаться приложение и виджеты). Код демо-режима (`DemoGate`) в сборке остаётся для fomo.spot.
- **API — тоже allowlist**: чужие маршруты отвечают `404 {"error":"Not found"}`. Проверка стоит в `server.ts` (видит все
  `/api/*`) и в middleware (дублирует для тех, что он видит). Открыты: `auth`, `captcha`, `terminal`, `calendar`,
  `economic-calendar`, `klines`, `quote(s)`, `market-search`, `contracts`, `orderbook`, `orderflow`, `algopack`, `futures` (только `spec` — калькулятор), `news`,
  `notifications`, `notification-settings` (в т. ч. вебхуки ботов), `push`, `telegram`, `me`, `languages`, `site-settings`,
  `version`, `upload`, `socketio`, `fomo-ideas` (см. ниже), `users` и `users/<id>` (профиль и список для админа), `admin/stats|broadcast|site-settings`.
- **Админка** `/admin` доступна только ADMIN / OWNER (проверяет middleware), в меню сайта ссылки на неё нет; в самой админке
  оставлены разделы «Пользователи», «Рассылка», «Настройки сайта».
- **Cookie** сессии: `terminal.session-token` (по http) или `__Secure-terminal.session-token`, `__Secure-terminal.callback-url`,
  `__Host-terminal.csrf-token` (по https). Без `Domain` (только свой хост). Сессия fomo.spot (`authjs.*`, другой секрет) здесь не
  читается, и наоборот. Ни в одном месте кода нет общего cookie-домена.
- **Настройки уведомлений**: матрица показывает «Терминал и календарь» (price_alert, line_alert, calendar_reminder) и «Система».
  Социальные события и платежи скрыты.
- **Нижнее меню приложения (app UI)**: Терминал, Настройки, Профиль. Календарь внутри терминала: на компьютере вкладка «Календарь» правой
  панели рядом со списком наблюдения, в app UI переключатель «Список наблюдения | Календарь» под рядом инструментов (`AppTerminal`).
- **Идеи и сообщество fomo.spot** (в терминале, не на лендинге): `GET /api/fomo-ideas?ticker=SBER[&alt=<dataTicker>]` — серверный прокси
  (`src/app/api/fomo-ideas/route.ts`, чистая часть `src/lib/fomo-ideas.ts`): только для вошедшего, на fomo.spot самом отвечает 404; тикер
  `^[A-Za-z0-9._-]{1,20}$`; сервер запрашивает `https://fomo.spot/api/instruments?search=` и `/api/ideas?instrumentId=&limit=5` (таймаут 4 с,
  без cookie), кэш в памяти 5 мин (сбой — 1 мин), при недоступности fomo.spot отвечает `{ok:false}` и интерфейс молчит. Ответ:
  `{ok, count, ideas:[{id,title,author,likes,createdAt,url}], boardUrl}`, `url` = `https://fomo.spot/ideas/<id>`. Показ: вкладка «Идеи FOMO» правой
  панели, карточка «Идеи FOMO по <тикер>» в app UI; ссылки открываются в новой вкладке (в Android-приложении fomo.spot — чужой хост, его
  открывает системный браузер). Карточка «FOMO — сообщество трейдеров» — под списком наблюдения и во вкладке идей, строка в профиле app UI.
- **Брендинг**: title/description «FOMO Terminal …», manifest «FOMO Terminal» (`start_url /terminal`, без share target),
  иконки `public/icons-terminal/*`, canonical и hreflang на `terminal.fomo.spot`, OG-картинка `public/landing/terminal/og.jpg`, нет Яндекс.Метрики и
  Google Analytics (счётчики fomo.spot), sitemap — только лендинг и юридические страницы, без обращений к базе. Тег подтверждения fomo.spot (Яндекс)
  здесь не выводится никогда; свои теги Google / Яндекса — только из `GOOGLE_SITE_VERIFICATION` / `YANDEX_VERIFICATION` (см. «SEO» ниже).
- **Socket.IO**: CORS только на адрес инстанса (на fomo.spot по-прежнему `*`).

## Единый аккаунт: зеркало между двумя базами

Решение владельца: «создание профиля в терминале = созданию профиля на fomo.spot и наоборот». Базы остаются раздельными (алерты,
списки наблюдения, идеи, подписки, чаты, сообщения, платежи **не** общие); между ними копируются только аккаунт и профиль. Код один, поэтому
одна и та же реализация работает в обе стороны.

**Выключатель.** Пока не заданы оба `ACCOUNT_MIRROR_SECRET` и `ACCOUNT_MIRROR_PEER_URL` (и секрет не короче 32 символов), зеркало
выключено целиком: вызовы отправки возвращаются сразу, эндпоинт отвечает 404, поведение сайтов прежнее. Поэтому код можно выкатить до
появления секрета. Включение: `bash scripts/setup-account-mirror.sh` на сервере (создаёт случайный секрет `openssl rand -hex 32`, **только если**
его нет в `/opt/fomo/.env`; дописывает тот же секрет и нужный `ACCOUNT_MIRROR_PEER_URL` в оба `.env`, остальные строки не трогает; перед правкой кладёт копию
каждого `.env` (`cp -p`) в закрытую папку `~/.fomo-env-backups` (режим 0700, путь выводится в строке `changed`, меняется переменной `BACKUP_DIR`), новый файл пишет рядом
под временным именем с теми же правами и владельцем и подменяет оригинал одним `mv`; секрет не печатает, выводит только строки `OK` / `changed`, ничего не перезапускает), затем деплой (`deploy-swap.sh` делает `pm2 restart --update-env`) или
`pm2 restart fomo fomo-terminal --update-env`. Порты берутся из `PORT` в `.env` каждого инстанса (по умолчанию 3000 и 3100).

**Что зеркалируется** (отправитель: тот сайт, где это произошло; вызовы в фоне, `src/lib/account-mirror-client.ts`):

| Событие | Где | Что получает другая сторона |
|---|---|---|
| Регистрация | `api/auth/register` | `register`: создать аккаунт (email, **хэш** пароля, профиль). Если там висит брошенный PENDING с этим адресом, он дописывается так же, как это делает локальная регистрация |
| Вход на **fomo.spot** (ленивая подтяжка) | `lib/auth.ts`, `authorize` после успешной проверки пароля | `ensure`: создать аккаунт на терминале, **только если** адреса там нет; существующий не трогается (разные пароли остаются разными до смены или сброса). Один запрос на адрес и процесс в 6 часов |
| Вход на **терминале** (сверка профиля) | то же место, `mirrorLogin` | `pull`: терминал просит у fomo.spot профиль того же адреса и применяет его у себя, **fomo.spot главный** (см. ниже). Если на fomo.spot такого адреса нет, терминал создаёт его там (`ensure`, как раньше). Один запрос на адрес и процесс в 6 часов |
| Смена пароля | `api/auth/change-password` | `password` с **старым и новым хэшем**: применяется, только если у аккаунта там сейчас тот же старый хэш (compare-and-swap); тогда новый хэш + `sessionVersion + 1` (старые сессии там тоже закрываются). Иначе `skipped/mismatch`: аккаунты с разными паролями остаются как есть |
| Сброс пароля | `api/auth/reset-password` (шаг `reset`) | `reset`: владение ящиком доказано кодом, поэтому новый хэш ставится без сравнения, но только обычному `USER`; `sessionVersion + 1` |
| Смена e-mail | `api/auth/change-email` (шаг `verify`) | `email` с текущим хэшем отправителя: найти по **старому** адресу, переименовать, `sessionVersion + 1`; только если у аккаунта там тот же хэш, иначе `skipped/mismatch` |
| Чтение своего профиля на терминале | `GET api/users/[id]` (свой id) | сверка `pull` для уже вошедших (см. ниже) |
| Правка профиля | `PATCH api/users/[id]` (профиль, аватар, ник/`fomoId`, в том числе правка админом), `POST api/me/locale` | `profile`: только изменённые поля из белого списка |

**Учётные данные привилегированных аккаунтов зеркало не меняет.** `password`, `reset`, `email` и дописывание брошенной регистрации применяются на стороне-получателе только к
пользователям с ролью `USER`; для `ADMIN` / `OWNER` ответ `skipped/privileged`, ничего не пишется. Поэтому взлом одного сайта (украденный пароль владельца и смена пароля через
обычный `change-password`) не переписывает пароль владельца на втором. Первый владелец терминала и админы живут каждый в своей базе.
**Операции только с профилем (`profile` и `pull`) работают для любой роли, `ADMIN` / `OWNER` включительно:** они несут только белый список полей отображения (имя, ник, аватар, имена,
город и т. д.), никогда роль, статус, бан, рейтинг, платёжные поля, e-mail или пароль, поэтому повысить права или войти под чужим аккаунтом через них нельзя; правки профиля владельца
должны доходить до второго сайта. Максимум, что даёт знание секрета, это подмена имени, ника или аватара привилегированного аккаунта на втором сайте.

**Сверка профиля при входе на терминале (`pull`).** Правки профиля идут только изменёнными полями, поэтому два уже существующих профиля с одним e-mail сами не сходятся. После успешного
входа **на терминале** (только там; fomo.spot источник истины и сам `pull` не отправляет, а на терминале на `pull` отвечает `not_found`) терминал шлёт подписанную операцию `pull` (только адрес;
направление `terminal>main`, те же подпись, окно, лимит 300/мин и правила 404) и получает от fomo.spot **белый список полей профиля и путь аватара**: в ответе нет хэша, роли, статуса, e-mail,
денежных полей, рейтинга и бана; адрес сопоставляется без учёта регистра, как вход. Затем терминал применяет профиль у себя (`applyPulledProfile`, код регистрируется модулем
`src/lib/account-mirror-pull.ts`, подключённым из маршрута next-auth): **главный fomo.spot, если у него в поле есть значение**. Пустое значение (null, пустая или из пробелов строка,
пустой список, объект ссылок без заполненных ключей) локальное **не затирает**. Значения по умолчанию колонок (`locale = ru`, `dmEnabled = true`) отличить от «не задано» нельзя, поэтому
они значениями не считаются. Аватар скачивается тем же безопасным кодом, что и при остальных операциях (путь по регулярке, только origin пира, лимит размера, проверка байтов, sharp,
файл по хэшу, прежний файл удаляется). `fomoId`: если id с fomo.spot занят другим локальным пользователем, поле пропускается (локальный остаётся), остальное применяется. Пароли и e-mail
этой операцией **не меняются** (выравниваются только сменой или сбросом пароля). Не чаще раза на адрес и процесс в 6 часов; любой сбой тихий и вход не задерживает (запрос идёт в фоне).
Правки после сверки идут как раньше (`profile`). Если у человека на двух сайтах **разные** e-mail, сверка ничего не найдёт: аккаунты не связаны.

Не зеркалируется: вход/выход, бан и роли, оценка, оплата, `terminal-instance-init.ts` (первый владелец создаётся только в своей базе), отправка кода
(`send-code`: пользователя не создаёт). Массовой миграции нет: существующие аккаунты появляются на другой стороне при первом входе.

**fomo.spot главный аккаунт.** Правило владельца: для одного e-mail логин и пароль одинаковые на обоих сайтах, главный аккаунт и данные на fomo.spot, даже если на терминале
зарегистрировались с другим профилем. Реализация (всё только на терминале, только при включённом зеркале; на fomo.spot терминал ничего не навязывает):

| Что | Как |
|---|---|
| **Выравнивание пароля при входе** (`verify`) | Вход на терминале, где введённый пароль не подошёл локальному аккаунту (или локального аккаунта нет): терминал одним подписанным запросом (`verify`, loopback, направление `terminal>main`) спрашивает fomo.spot, верен ли пароль для этого адреса. **Открытый пароль есть только в теле этого одного запроса**: не логируется, не хранится. Если вопрос вообще не задаётся: локальный аккаунт **BANNED или не `APPROVED`** (тогда ни вопроса, ни замены хэша), сработала **локальная квота терминала на `verify` (10 за 15 минут на адрес посетителя**, ключ `verify:local:ip:`, чтобы форма терминала не выбирала общий лимит fomo.spot), fomo.spot минуту назад не отвечал (отрицательный кэш). Для несуществующего локального аккаунта пароль сравнивается с «пустышкой» bcrypt (cost 10), чтобы ответ не выдавал, есть ли такой адрес. fomo.spot проверяет по своей базе, аккаунт должен быть `APPROVED` (бан и незавершённая регистрация там действуют), и отвечает одинаково на любой отказ (`denied`: неверный пароль, неизвестный адрес, бан, превышение лимита, адрес посетителя не IP); для неизвестного адреса всё равно делается сравнение bcrypt. **Успешный ответ (подписанный, по loopback) несёт хэш пароля главного аккаунта и канонический e-mail главного аккаунта** (хэши по loopback fomo.spot → терминал ходят только в этом ответе, в обратную сторону хэши идут в `register` / `ensure` / `password` / `reset`, как раньше). Терминал **сохраняет именно этот хэш** (второй bcrypt с новой солью не считается, поэтому хэши на двух сторонах совпадают и compare-and-swap операции `password` / `email` продолжают работать), приводит аккаунт к каноническому e-mail (найденный под другим регистром или старым адресом аккаунт **переименовывается, второй не создаётся**; адрес, занятый другим локальным аккаунтом, не отбирается), поднимает `sessionVersion` (старые сессии закрываются), применяет профиль главного (главный побеждает) и завершает вход. Нет локального аккаунта: создаётся под каноническим адресом (поиск существующего всегда без учёта регистра). Разрешено для **любой роли**: доказательство это пароль главного аккаунта. Один запрос без повторов (таймаут 3 с); недоступный fomo.spot или отказ = обычное «неверный логин или пароль», вход не падает |
| **Лимиты `verify`** | fomo.spot считает каждую проверку в **отдельных** счётчиках, не в счётчиках настоящего входа: `verify:email:<адрес>` **5 за 15 минут** и `verify:ip:<адрес посетителя>` **20 за 15 минут** (адрес посетителя терминал передаёт в запросе; fomo.spot принимает только литерал IP, проверка `net.isIP`, иначе отказ без подсчёта). Так форма терминала не может заблокировать человеку вход на самом fomo.spot (`login:email:` не трогается); успех сбрасывает только `verify:email:`. Адрес приводится к виду «обрезан (пробелы, табы, NBSP) и в нижнем регистре» одной и той же функцией (`normalizeLoginEmail`) в обычном входе обоих сайтов и в `verify`: варианты с пробелами и регистром делят один счётчик, а не получают по десять попыток. Плюс собственная корзина входящих `verify` 120/мин. Свои лимиты входа на терминале действуют до этого |
| **Регистрация на терминале** (`exists`) | После кода из письма (ящик доказан) терминал спрашивает fomo.spot, какой статус у этого адреса. «Существует» только **`APPROVED`** аккаунт (или другое написание того же gmail-ящика среди `APPROVED`): второй аккаунт не создаётся, ответ 400 «адрес уже зарегистрирован на fomo.spot, войдите с логином и паролем от fomo.spot» (`api.accountExistsOnMain`, ru/en/cn). Незавершённая (`PENDING`) регистрация на fomo.spot не блокирует (человек регистрируется), `BANNED` получает обычное сообщение о блокировке (403). Нет ответа fomo.spot (недоступен, медленный): регистрация идёт как раньше, расхождение потом разрешает правило входа. Ответ несёт статус аккаунта, но ни профиля, ни хэша |
| **Регистрация на fomo.spot** | Не блокируется терминалом: главный аккаунт создаётся с новым паролем, на терминал уходит `register`; если там уже был аккаунт с этим адресом, он остаётся как есть и подхватит пароль главного при первом входе введённым паролем fomo.spot (`verify`) |
| **Смена и сброс пароля на терминале** | Работают и зеркалируются на fomo.spot по прежним правилам (compare-and-swap для смены, только `USER` для обоих). Если на fomo.spot адрес принадлежит `ADMIN` / `OWNER`, пароль там меняется только на fomo.spot: терминал отвечает 403 «меняйте пароль на fomo.spot» (`api.passwordManagedOnMain`), следующий вход на терминале выровняет пароль по правилу `verify`. Определяется операцией `exists` по адресу, **сохранённому в аккаунте** (после кода для сброса, после проверки текущего пароля для смены). **Если ответа нет** (fomo.spot недоступен, 429, 5xx, таймаут): для обычного локального аккаунта всё идёт как раньше (fail-open), а для локального `ADMIN` / `OWNER` **fail-closed**: 503 «повторите позже» (`api.tryAgainLater`). Тело запроса сброса пароля принимается только со строковыми полями (иначе 400). Смена e-mail на терминале для таких аккаунтов не блокируется (зеркало её для привилегированных всё равно пропускает) |
| **Профиль** | Главный побеждает при `pull` (см. выше); `pull` выполняется и сразу после успешного выравнивания (профиль применяется самим выравниванием, повторного запроса нет). Правки профиля на терминале по-прежнему зеркалируются на fomo.spot (`profile`, последняя запись побеждает) |

Компромиссы безопасности. (1) Открытый пароль один раз пересекает loopback при выравнивании; защищён подписью HMAC (направление, метод, путь, окно 60 с, nonce), маршрут закрыт для всего, что пришло через nginx,
не логируется и не сохраняется. Кто владеет секретом зеркала и может подписывать запросы, может использовать `verify` как оракул пароля, но только в пределах тех же лимитов входа fomo.spot и без обхода бана. (2) Для любой роли:
знание пароля главного аккаунта даёт вход и в терминальный аккаунт того же адреса, какую бы роль тот там ни имел (на терминале роли свои); украденный пароль fomo.spot открывает и терминал. (3) Пока fomo.spot недоступен, вход на терминале работает
по локальному паролю, расхождение (если оно было) сохраняется до первого входа с паролем главного.

**Адрес посетителя для лимитов.** `clientIp` (`src/lib/rate-limit.ts`) раньше брал ПЕРВЫЙ элемент `X-Forwarded-For`, а его задаёт сам посетитель (nginx с `$proxy_add_x_forwarded_for`
сохраняет присланное и ДОБАВЛЯЕТ адрес, который видел сам): подставляя другой адрес в каждом запросе, любой счётчик «на источник» обходился. Теперь берётся **последний** элемент (добавленный нашим nginx),
без `X-Forwarded-For` `X-Real-IP`, без заголовков прокси `unknown`, как раньше. Если перед nginx появится ещё один доверенный прокси (CDN), нужно брать предпоследний элемент: сегодня такого нет.
Это меняет ключ всех лимитов «на источник» (вход, регистрация, коды, котировки) только для тех, кто присылал лишние элементы.

**Проверка адресов и стоимость.** Поиск «другого написания того же ящика» (точки и `+` у gmail) без индексированной колонки требует выборки адресов всех `APPROVED` аккаунтов. Выборка берёт только e-mail и роль,
результат хранится в памяти процесса **60 секунд** (на базу), сбрасывается при регистрации, смене e-mail и выравнивании в этом процессе; устаревший ответ возможен не дольше минуты. Ограничение: пока нет колонки
`emailNormalized` с индексом (изменение схемы и миграция, сейчас не делаются), каждая выборка линейна по числу пользователей. **Отрицательный кэш:** после неудачного `pull` / `verify` / `exists` (fomo.spot не ответил)
следующие такие вопросы в этом процессе минуту пропускаются, чтобы недоступный fomo.spot не добавлял по 2,5 с к каждому чтению профиля и по 3 с к каждому входу (для вопросов `exists` ответ в это время «нет ответа»).

**Сверка профиля для уже вошедших пользователей.** Cookie сессии живёт 30 дней, повторно логиниться человек не обязан, поэтому та же сверка (`pull`) запускается при чтении **собственного профиля**: `GET /api/users/<свой id>`
(страница профиля и экран профиля приложения). Только терминал, только при включённом зеркале, тот же троттлинг (раз на адрес и процесс в 6 часов, проверка в памяти, без записи в базу). Когда сверка нужна, чтение ждёт её до 2,5 с, так что
первый ответ уже содержит слитый профиль; если fomo.spot медленный, запрос не задерживается дольше, а следующее чтение свежее. Если на fomo.spot такого адреса нет, терминал создаёт его там (запись целиком подгружается только в этот момент).
Кэш service worker или офлайн-копия страницы может на один показ вернуть старый профиль.

**Логи.** По одной строке на исход `pull` (без адресов): `pull: pulled (fields: ...)`, `pull: nochange`, `pull: skipped (...)`, `pull: failed:<причина>` (`unreachable`, `timeout`, `http_5xx`, `peer_off_or_secret`, `invalid_data`, `bad_profile`, `apply_error`);
для `verify`: `verify: aligned (password|created)`, `verify: denied`, `verify: failed:<причина>`. Проверка: `pm2 logs fomo-terminal | grep account-mirror`.
**Когда `pull` законно ничего не делает:** зеркало выключено или не настроено (нет секрета или адреса пира); троттлинг (раз в 6 часов на адрес и процесс, рестарт процесса сбрасывает); на fomo.spot нет аккаунта с таким адресом (e-mail на сайтах разный: адреса сопоставляются без учёта регистра,
но это один и тот же ящик, другие ящики не связываются); у главного поля пустые (пустое локальное не затирает) или равны значениям по умолчанию (`locale = ru`, `dmEnabled = true` значениями не считаются); профили уже совпадают (`nochange`); локальный аккаунт не `APPROVED`;
`fomoId` главного занят другим локальным пользователем (поле пропускается); аватар не скачался (`skipped: avatarUrl`); fomo.spot недоступен (три попытки, тихо); сам fomo.spot `pull` не выполняет.

**Белый список полей профиля** (`PROFILE_FIELDS` в `src/lib/account-mirror.ts`; `scripts/check-account-mirror.ts` сверяет его со `schema.prisma`:
каждое скалярное поле `User` обязано быть либо в белом списке, либо в списке исключений, иначе проверка падает):

| Поле | Решение |
|---|---|
| `displayName`, `firstName`, `lastName`, `bio`, `birthDate`, `city`, `workplace`, `exchangeExperience`, `specializations`, `socialLinks`, `locale`, `dmEnabled` | зеркалируются |
| `fomoId` (ник, уникальный идентификатор) | зеркалируется; при создании берётся тот же, а если он занят другим пользователем на той стороне: `<id>_<4 hex от sha256(email)>` (детерминированно), затем случайный; ответ несёт `fomoIdChanged`, в лог пишется `(fomoId changed)`. При последующей смене, если нужный id там занят, поле пропускается (`skipped: fomoId`), остальное применяется |
| `avatarUrl` | зеркалируется как **файл** (см. ниже) |
| `email`, `passwordHash` | отдельные операции (`email`, `password`), в `profile` не передаются |
| `role`, `status`, `bannedUntil`, `banReason` | **не зеркалируются**: админ одного сайта не управляет другим; новый аккаунт всегда `APPROVED` / `USER` (в формате сообщения этих полей нет) |
| `rating`, `ratingBonus`, `lastPublishedAt` | не зеркалируются (счётчики сервиса идей) |
| `sessionVersion` | не зеркалируется; увеличивается на стороне-получателе при смене пароля или e-mail |
| `subscriptionPrice`, `paymentCard`, `donationCard`, `sbpQrUrl` | не зеркалируются (деньги и платные сервисы fomo.spot) |
| `id`, `createdAt`, `updatedAt` | локальные |
| связи (`Education`, идеи, тарифы, алерты ...) | не зеркалируются |

**Аватарки.** Загрузка кладёт 200x200 JPEG в `public/uploads/avatars/<userId>/<uuid>.jpg`, `avatarUrl` относительный (`/uploads/avatars/...`), а `/uploads/*`
отдаёт `server.ts` самого инстанса; у второго сайта такого файла нет, поэтому относительная ссылка там была бы битой. Решение: в сообщении идёт **только
путь**, получатель сам скачивает файл у пира (`ACCOUNT_MIRROR_PEER_URL` + путь, loopback), проверяет путь регуляркой
`/uploads/avatars/<id>/<имя>.(jpg|jpeg|png|webp|gif)`, не следует редиректам, ограничивает размер (2 МБ), проверяет формат по первым байтам (а не по
`Content-Type`), перекодирует через sharp в 200x200 JPEG (не больше 25 млн пикселей, строгое декодирование) и сохраняет в **свой** `public/uploads/avatars/<свой userId>/`; имя файла это хэш содержимого, поэтому повтор
сообщения пишет тот же файл, а прежний файл аватара этого пользователя в его папке удаляется при замене или удалении. Скачивание у получателя ограничено 4 с, отправитель
для сообщений с аватаром ждёт ответа 9 с. Итог: аватар не зависит от
доступности другого сайта, сторонних адресов в `avatarUrl` не появляется (внешние URL в аватарке не зеркалируются вовсе), хотлинка нет. Если скачать не удалось,
аватар на другой стороне остаётся прежним (`skipped: avatarUrl`), остальные поля применяются. Удаление аватара (`null`) зеркалируется.

**Транспорт.** Только сервер-сервер: `POST {PEER_URL}/api/internal/account-mirror` (маршрут `src/app/api/internal/account-mirror/route.ts`, на терминале
разрешён точечно в `routeAllowed`; остальные `/api/internal/*` закрыты). Заголовки `x-mirror-timestamp` (мс), `x-mirror-nonce`, `x-mirror-signature` =
hex HMAC-SHA256(секрет, `mirror-v1|POST|/api/internal/account-mirror|<от>><кому>|timestamp|nonce|тело`): в подписанный текст входят версия, метод, путь и направление
(`main>terminal` / `terminal>main`), поэтому перехваченный запрос нельзя отразить обратно или применить к другому маршруту. Получатель: окно 60 с, nonce запоминается на 120 с (повтор = 404), сравнение за постоянное время,
тело не больше 64 КБ, затем zod-схема, затем лимит (после проверки подписи, чтобы чужие запросы не съедали лимит пира): **60 в минуту** отдельно для `register` / `password` / `reset` / `email`
**120 в минуту** для `verify` и **300 в минуту** для `profile` / `ensure` / `pull` / `exists`, чтобы поток правок профиля и входов не мог вытеснить смену пароля. Неверные данные логируются именем поля, без значений. **404** (а не 401) при
незаданном секрете, неверной подписи, повторе nonce и любом методе кроме POST; 400 для верной подписи и неверных данных. Ответ несёт только `result`
(`created`, `completed`, `exists`, `alias_conflict`, `updated`, `noop`, `not_found`, `conflict`, `pulled` с полем `profile`, `skipped` с `reason` `privileged` / `mismatch`) и поля `skipped` / `fomoIdChanged`; хэшей и адресов там нет.
Идемпотентность: создание «если нет», правка «если совпало», повтор даёт `exists` / `noop`. Получатель никогда не вызывает отправку, зацикливания нет.
Отправитель: таймаут 3,5 с на попытку (9 с для сообщений с аватаром); на 5xx, 429 и сетевые ошибки `profile` / `ensure` / `pull` пробуются 3 раза (сразу, через 0,4 и 1,2 с), а
**`register` / `password` / `reset` / `email` около 5 минут** (паузы 0; 0,4; 1,2; 4; 12; 30; 60; 90; 120 с), чтобы переживать рестарт пира при деплое (`deploy-swap.sh` перезапускает
оба инстанса). 404 и 400 не повторяются (400 пишется в лог с именем операции, без данных). Если пир отвечает `not_found` на `password` / `reset` / `profile`
(переименование или копия регистрации ещё в пути), отправка ждёт 2, 5 и 10 с и пробует снова. Очередь по одному аккаунту ключуется по **id пользователя отправителя**,
поэтому после смены e-mail сначала уходит переименование, а следующие сообщения ждут его. Таймеры повторов не удерживают процесс при остановке.
**Постоянной очереди (outbox) нет, и таблицы под неё нет:** повторы живут только в памяти процесса отправителя. Сообщение, которое не доставлено за ~5 минут, или то,
что ещё ждало повтора в момент остановки/рестарта процесса отправителя, **теряется**; регистрация и вход догоняются следующим входом (`ensure`), смена пароля/e-mail и правка
профиля нет (аккаунты временно расходятся, пока их не выровняет следующая смена пароля или правка). Сбой зеркала **никогда** не влияет на локальную операцию (она уже выполнена,
отправка идёт в фоне). Повторный `POST /api/me/locale` с тем же языком ничего не пишет и не зеркалирует; форма профиля зеркалирует только действительно изменившиеся поля.
В логи попадают только операция и исход, без адресов, хэшей и секрета.

**Обязательные шаги на сервере (nginx и фаервол).** Пиры общаются по loopback (`127.0.0.1:3000` и `127.0.0.1:3100`), публичные vhost'ы этот маршрут проксировать не должны.
В **обоих** публичных vhost'ах (fomo.spot и terminal.fomo.spot) добавить перед общим `location /`:

```nginx
location = /api/internal/account-mirror {
    client_max_body_size 64k;
    return 404;
}
```

(в vhost терминала, который печатает `terminal-instance-setup.sh nginx`, блок уже есть; в vhost fomo.spot, которого нет в репозитории, добавить вручную), затем `sudo nginx -t && sudo systemctl reload nginx`.
Проверка: `curl -s -o /dev/null -w "%{http_code}\n" -X POST https://fomo.spot/api/internal/account-mirror` и то же для terminal.fomo.spot дают 404 уже от nginx.
Кроме того, `server.ts` слушает `0.0.0.0`: порты **3000 и 3100 должны быть недоступны снаружи**, проверьте фаервол (`ufw status`, правила провайдера Timeweb): снаружи
`curl http://<IP сервера>:3000/` и `:3100` не должны отвечать. Даже при открытом порте маршрут без верной подписи отвечает 404, но лишний открытый порт обходит nginx
(лимиты, заголовки, TLS), этого быть не должно.

**Порядок записей и конфликты.** Побеждает последняя пришедшая запись (поле `updatedAt` для этого не годится: Prisma меняет его при любой записи, например при
пересчёте рейтинга, и честная правка профиля могла бы отброситься). Одновременные правки одного поля на двух сайтах: остаётся то, что пришло позже.
Адрес, уже занятый на другой стороне, остаётся с тем паролем, который там был: пароли выравнивает смена или сброс пароля. Другое написание того же ящика
(точки и `+` в gmail) на стороне-получателе не создаётся (`alias_conflict`), как и при локальной регистрации.

**Проверка:** `npx tsx scripts/check-account-mirror.ts` (подпись и её область, окно, nonce, схема, белый список, обрезка значений на отправителе, статус, fomoId, аватар,
правила получателя на фейковой базе: учётные данные привилегированных аккаунтов, синхронизация их профиля, compare-and-swap пароля, смена e-mail, регистрация, идемпотентность; сверка при входе: форма ответа `pull`, слияние «главный побеждает», пустое не затирает; отправитель против фейкового пира:
повторы, порядок, лимиты).
Сквозная проверка нужна на двух запущенных серверах: после деплоя и `setup-account-mirror.sh` завести временный аккаунт на терминале, убедиться, что на fomo.spot он входит тем же паролем
(в логе `pm2 logs fomo` строка `[account-mirror] register: created`), поменять ник и аватар на fomo.spot и увидеть их в профиле терминала, сменить пароль и e-mail,
затем удалить временные аккаунты.

### Разовая сверка баз: `scripts/sync-accounts.ts`

Живое зеркало ловит новые события; чтобы **сразу** привести обе базы к одному состоянию («в двух сервисах одинаковые аккаунты у всех»), есть разовый скрипт, который работает с двумя базами напрямую.
fomo.spot (main) главный, терминал приводится к нему. Скрипт по умолчанию **ничего не пишет** (ни строк базы, ни файлов).

```bash
cd /opt/fomo
npx tsx scripts/sync-accounts.ts                       # 1. сухой прогон: только отчёт, ничего не записано
npx tsx scripts/sync-accounts.ts --apply               # 2. запись
npx tsx scripts/sync-accounts.ts --apply --terminal-only-to-main   # (по желанию, по умолчанию выключено) ещё и создать на main аккаунты, которые есть только на терминале
npx tsx scripts/sync-accounts.ts                       # 3. повторный запуск должен показать 0 изменений
```

Пути к `.env` по умолчанию `/opt/fomo/.env` и `/opt/fomo-terminal/.env` (`--main-env`, `--terminal-env`); `DATABASE_URL` берётся оттуда, адреса и пароли не печатаются. Скрипт откажется работать, если обе базы
одна и та же, если в `.env` терминала нет `SITE_MODE=terminal` (или в `.env` main он есть: перепутаны аргументы; `--force` отключает эту проверку), или при незнакомом аргументе. Файлы аватаров берутся из `public/` рядом с
соответствующим `.env`.

**Что делает.**

| Случай | Действие |
|---|---|
| Аккаунт есть на обеих сторонах (сопоставление по e-mail без учёта регистра и пробелов) | терминал := main: хэш пароля (`sessionVersion + 1` только если хэш изменился), e-mail (написание main), все поля профиля из белого списка, у которых **на main есть значение** (пустое на main терминал не затирает; `locale = ru` и `dmEnabled = true` значениями не считаются, как в зеркале), `fomoId` main (если его не занял другой аккаунт терминала: тогда остаётся локальный, это в отчёте), **аватар**: файл копируется из `public/uploads/avatars/<id на main>/` в `public/uploads/avatars/<id на терминале>/` с тем же безопасным перекодированием, что у зеркала (200x200 JPEG, лимиты размера и пикселей, имя файла = хэш содержимого) |
| Только на main, статус `APPROVED` | создаётся на терминале (`USER`, `APPROVED`, тот же хэш и профиль, аватар скопирован) |
| Только на main, не `APPROVED` | не создаётся, считается в отчёте |
| Только на терминале | **не создаётся на main** (эти люди согласились на условия отдельного аккаунта терминала, на main они стали бы участниками соцсети); в отчёте всегда выводится их число. С `--terminal-only-to-main`: `APPROVED` создаются на main (`USER`, `APPROVED`, тот же хэш и профиль, аватар) |
| Алиасы (gmail с точками или `+`, которые `normalizeEmail` считает одним ящиком, но строки разные) и адрес, повторяющийся в одной базе | пропускаются и перечисляются, **никогда не склеиваются** |

Роль, статус, бан, рейтинг и платёжные поля существующих аккаунтов **не трогаются**, ничего не удаляется. Каждая запись это один `update` или `create` на пользователя внутри `try/catch` (ошибка одного не
останавливает остальных; код выхода 1, если ошибки были). Файл аватара пишется до строки базы, при сбое записи строки файл остаётся лишним, но безвредным.

**Отчёт.** Таблица счётчиков (на обеих сторонах всего, совпавшие без изменений, совпавшие с изменениями по группам password / profile / avatar / email, созданные на терминале, только на main не `APPROVED`,
только на терминале, конфликты, занятый `fomoId`, недостающие файлы аватаров, ошибки) и по строке на изменённый, созданный или конфликтующий аккаунт: только id и маскированный адрес (`a***@domain`),
никаких хэшей и паролей.

**ВНИМАНИЕ.** `--apply` **заменяет пароли терминала на пароли главного аккаунта** у всех совпавших пользователей: старый пароль, который работал только на терминале, перестанет работать, и сессии
этих людей на терминале закроются (для тех, у кого хэш изменился). Сделайте резервную копию базы терминала (`pg_dump`) и просмотрите сухой прогон. Сначала сухой прогон, потом `--apply`.

### 1. Сервер: код, база, `.env`, сборка, pm2


`all` = `env` → `db` → `install` → `vapid` → `init` → `build` → `pm2` → `nginx` (печатает vhost). Каждый шаг можно запускать отдельно:

| Шаг | Что делает |
|---|---|
| `env` | создаёт `/opt/fomo-terminal/.env` (chmod 600): режим, адрес, `DATABASE_URL` с **сгенерированным** паролем, **новый** `AUTH_SECRET`; ключи — пустые. Существующий `.env` не трогает |
| `db` | от `postgres` создаёт роль `fomo_terminal` и базу `fomo_terminal` (идемпотентно) |
| `install` | `npm ci`, `prisma generate`, `prisma db push --skip-generate` (схема пустой базы целиком из `schema.prisma`) |
| `vapid` | генерирует VAPID-ключи web push для инстанса (публичный — переменная **сборки**) |
| `init` | языки, `SiteSettings` и **первый владелец** (см. ниже) |
| `build` | `npm run build` с `NEXT_PUBLIC_*` из `.env` |
| `pm2` | `ecosystem.terminal.config.cjs` (в корне checkout, в git не попадает), `pm2 start`, `pm2 save` |
| `nginx` | печатает vhost; `INSTALL_NGINX=1 bash … nginx` кладёт его в `sites-available` |
| `certbot` | `certbot --nginx -d terminal.fomo.spot` (`CERTBOT_EMAIL=… ` — необязательно) |

Те же команды руками (если не хочется скрипта):

```bash

sudo -u postgres psql -c "CREATE DATABASE fomo_terminal OWNER fomo_terminal;"
# из /opt/fomo-terminal
npm ci && npx prisma generate && npx prisma db push --skip-generate
```

Порт по умолчанию `3100` (`PORT=… bash scripts/terminal-instance-setup.sh …` меняет и `.env`, и nginx, и pm2). `fomo.spot`
остаётся на своём порту под `/opt/fomo`.

### 2. Схема базы: `db push`, а не миграции
Миграции из `prisma/migrations` — идемпотентные SQL-патчи для **существующей** базы fomo.spot (их применяют
`prisma db execute`). Для пустой базы правильно `prisma db push`: он строит всё из `schema.prisma` (так же делают `Dockerfile` и
`railway.toml`). Проверено по файлам миграций: объектов вне схемы нет — ни расширений, ни функций, ни триггеров, ни частичных
индексов; все 61 `CREATE INDEX` из миграций объявлены в `schema.prisma` (`@@index`, `@@unique`, `@unique`), enum'ы тоже в схеме.
Данных-«сидов» миграции не создают. Поэтому ничего дополнительно применять не нужно.
Нужные приложению стартовые строки (языки для переключателя, `SiteSettings`, владелец) создаёт `init`.

Новые изменения схемы: `git pull` → `npx prisma db push --skip-generate`. Если Prisma предупреждает о потере данных, **не** добавляйте
`--accept-data-loss` вслепую: сначала бэкап (`pg_dump`).

### 3. Первый владелец (ADMIN/OWNER) на пустой базе
`prisma/seed.ts` **не запускать**: он создаёт тестовых пользователей с известными паролями и демо-контент fomo.spot.

```bash
bash scripts/terminal-instance-setup.sh init      # спросит e-mail и пароль (пароль не отображается)
# или без вопросов:
OWNER_EMAIL=you@example.com OWNER_PASSWORD='…' bash scripts/terminal-instance-setup.sh init
```

`scripts/terminal-instance-init.ts` берёт e-mail и пароль только из окружения, хеширует тем же bcrypt (cost 10), что и
регистрация, создаёт пользователя с ролью `OWNER` и статусом `APPROVED` (или у существующего сбрасывает пароль и закрывает
старые сессии). Он откажется работать, если в имени базы нет слова `terminal` (защита от запуска по базе fomo.spot; `--force` — на свой риск).
Остальные люди регистрируются сами на `/register` (код приходит по e-mail, одобрение не нужно), роли выдаются в `/admin/users`.

### 4. Ключи в `/opt/fomo-terminal/.env` (вписать вручную, секреты в git не попадают)
- `RESEND_API_KEY` — без него никто не сможет зарегистрироваться (код приходит письмом). Домен отправителя должен быть подтверждён в Resend;
  по умолчанию `EMAIL_FROM="FOMO Terminal <no-reply@fomo.spot>"`.
- `FCM_SERVICE_ACCOUNT_FILE=<тот же файл, что у /opt/fomo>` — ключ сервис-аккаунта проекта `fomo3-c2798` (приложение `spot.fomo.terminal` добавлено в тот же Firebase-проект, отдельный проект и ключ не нужны)
  (Firebase → Project settings → Service accounts → Generate new private key; файл вне репозитория, `chmod 600`, читает пользователь pm2).
  `project_id` берётся из самого файла, `FCM_PROJECT_ID` не нужен.
- По желанию: `TINKOFF_TOKEN` / `TINKOFF_READONLY_TOKEN`, `ALGOPACK_KEY`, `FMP_API_KEY`, `TELEGRAM_BOT_*`. Ключи fomo.spot можно использовать
  повторно только осознанно: у MOEX ALGOPACK и Tinkoff есть лицензионные условия.

После правки `.env`: `pm2 restart fomo-terminal --update-env`; если менялись `NEXT_PUBLIC_*` — пересборка.

### 6. Обновление инстанса (swap-deploy, как у /opt/fomo)
```bash
cd /opt/fomo-terminal && git pull --ff-only && npm install --no-audit --no-fund && npx prisma generate && npx prisma db push --skip-generate \
 && NEXT_DIST_DIR=.next-build npm run build && rm -rf .next-old && mv .next .next-old && mv .next-build .next \
```

  `src/lib/i18n/dict/termlegal.ts`, раскладка разделов и проверка ключей — `src/lib/terminal-legal.ts`, страница —
  `src/components/legal/TerminalLegal.tsx`); на fomo.spot остаются прежние тексты. Это **черновики**: перед тем как на них опираться,

  (см. таблицу выше); пока не задан, написано «форма обратной связи на https://fomo.spot» и адрес не печатается. Если меняются состав
  данных, обработчики (Resend, FCM, Telegram, Timeweb), cookie или появляется оплата/аналитика, поправьте тексты и дату
  (`TERMINAL_LEGAL_DATE`, ключи `effective`, `TERMINAL_STATIC_LASTMOD`). Проверка: `npx tsx scripts/check-site-mode.ts`.
